# GhostRide 👻

**Project:** Browser automation for syndicating blog posts to social media.
**Mechanism:** Uses Claude's "Computer Use" / Browser capability to ghost-ride the active Chrome session.

**Note:** See `TOOLS.md` for shot-scraper and trafilatura CLI reference when debugging or modifying capture scripts.

## 🔧 Preparation (One-Time Setup)

Before running GhostRide for the first time:
```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
shot-scraper install
```

## 🚀 Quick Start

When you publish a new blog post to WordPress:
```bash
./ghostride.sh https://abhyrama.com/your-new-post-url/
```

This will automatically:
1. Extract blog text using Trafilatura → `latest-post.txt`
2. Capture clean screenshot → `blog-screenshot.png`
3. Copy screenshot to clipboard
4. Launch Claude to create social media drafts

**Why auto-run?**
- Prevents clipboard security issues (no chance to copy passwords/sensitive data)
- No timing gap between preparation and execution
- One command does everything

## 📁 Code Structure

### Shell Scripts

**`ghostride.sh`** - Main automation script
- Extracts blog text with Trafilatura (hybrid: `--formatting` for text + `--json` for metadata)
- Captures screenshot with shot-scraper via `capture-blog.sh`
- Copies screenshot to clipboard (macOS `osascript`)
- Launches Claude with the GhostRide routine

**`capture-blog.sh`** - Screenshot helper
- Uses shot-scraper to capture clean blog screenshots
- Removes WordPress cruft (actionbar, share buttons, comments)
- Optimized dimensions for Twitter (1600px width, scale-factor 1.5)

### Generated Files

- `latest-post.txt` - Extracted blog content (title + formatted text with paragraph spacing)
- `blog-screenshot.png` - Screenshot for Twitter image posts

Both files are in `.gitignore` and excluded from version control.

## 🤖 Routines

Execution instructions for Claude live in `ROUTINES/` as self-contained Markdown files.

**`ROUTINES/ghostride.md`** - The main social media posting routine
Contains step-by-step browser automation instructions for:
- Twitter (image post with clipboard paste)
- LinkedIn (text post with 3000 char truncation)
- Facebook (text post with 63,206 char truncation)

The `ghostride.sh` script loads this routine and passes it to Claude along with the blog post URL:
```bash
claude --chrome -p "$(cat ROUTINES/ghostride.md)

post_url: $BLOG_URL"
```

This separation keeps development context (this file) separate from execution instructions (ROUTINES/).

# GitHub Issue & Branch Workflow

**Rules:**
1. **Don't commit directly to `main`.** All work happens on feature branches.
2. **Reference a GitHub issue (`#N`) in every commit's subject line**, which stays within 72 characters.
3. **Start work only from a GitHub issue.** No issue means no work.
4. **Make changes on the current branch.** Don't switch to `main` or any other branch to make edits: all file changes, commits and fixes happen on whatever branch you are on. A change that needs to land on `main` gets there through a PR, not by checking out `main` and editing it.

Git hooks enforce rules 1 and 2 and block a commit that breaks them (see Git Hooks below).

---

### Step 1: Create or Find a GitHub Issue

Before touching any code, ensure a GitHub issue exists:

```bash
# Search for existing issues
gh issue list --state open

# Create one if none exists
gh issue create --title "Clear, specific title" --body "Context and expected outcome"
```

- Use specific titles: "Fix overflow on mobile" not "Fix bug"
- Add labels: `bug`, `enhancement`, `documentation`, etc.

### Step 2: For Large Work -- Use the Epic/Sub-Issue Pattern

If the work involves multiple logical steps, files, or concepts:

1. **Create an epic issue** describing the full scope of work
2. **Break it into sub-issues**, each referencing the epic:
   ```bash
   # Create the epic
   gh issue create --title "Redesign detail page" --body "Epic for redesign..."
   # Suppose this is #10

   # Create sub-issues that reference the epic
   gh issue create --title "Add metadata section" --body "Part of #10. ..."
   gh issue create --title "Improve card styling" --body "Part of #10. ..."
   gh issue create --title "Add responsive layout" --body "Part of #10. ..."
   ```
3. **Work on sub-issues individually** -- each gets its own commits
4. **Close sub-issues as they are completed**
5. **Close the epic only when ALL sub-issues are done**:
   ```bash
   gh issue close 10 --comment "All sub-issues completed."
   ```

**When to use epics:** If the work will take more than ~3 commits or touches more than ~3 files, it's an epic.

### Step 3: Create a Feature Branch

```bash
# Branch naming: <issue-number>-short-description
git fetch origin && git checkout -b 42-fix-overflow origin/main
```

- One branch per issue (or per epic if sub-issues are tightly coupled)
- Always name the base, `origin/main`: sessions can share a checkout, so HEAD may be on another session's branch, and Claude Code's `git-branch-base.sh` hook blocks a bare `git checkout -b` / `git switch -c` (dotfiles#239)

### Step 4: Keep the Issue Updated

As you work, **post comments on the issue** to document your thought process and findings:

```bash
# Share investigation findings
gh issue comment 42 --body "Root cause identified: ..."

# Note key decisions -- including alternatives and why they lost:
# write the body to a file first, then pass the file
gh issue comment 42 --body-file decision-42.md

# Log progress on multi-step work
gh issue comment 42 --body "Desktop layout fixed. Moving on to mobile next."
```

- **A body longer than a sentence goes in a file, passed with `--body-file`** (`gh issue comment`, `gh issue create`, `gh pr create`; `gh issue close` takes `--comment` only, so keep it short and comment first). Inline `--body "…"` breaks on the content these comments carry: backticks in double quotes run as command substitution (`accepts 1 arg(s), received 4`). A HEREDOC or `--body "$(cat f)"` fixes the quoting but is still computed text, which the worktree-isolation guard refuses (dotfiles#611).
- Comment whenever you discover something relevant (root cause, unexpected behavior, design decision)
- **Document design tradeoffs, not just decisions.** When a decision involves alternatives, the comment must list the options considered, their tradeoffs, and why the chosen one won. A future reader should be able to reconstruct the reasoning -- why *this* approach over the others -- not just see the outcome.
- Comment when switching between sub-tasks or phases of work
- **Post the finalized plan on the issue before starting implementation.** Once a plan is iterated on and approved, comment on the issue with the full plan. This creates a durable record of intent outside the conversation.
- **Post deviations from the plan as they happen.** If implementation reveals that the plan needs to change, comment on the issue explaining what changed and why. The issue should always reflect the current state of the work, not just the original plan.
- **Every change must have its rationale on the issue.** Before the work is complete, each change in the diff must be explainable by something posted on the issue -- the plan, a decision comment, or a deviation note. If a change is not covered by any of those (a drive-by refactor, a small fix made in passing, incidental cleanup), post a comment explaining why it was made. A change whose "why" exists only in the conversation or a commit message is untraceable.
- The issue should read as a clear narrative of what was investigated, planned, decided, and done

### Step 5: Do Work and Commit

Every commit **subject line** (its first line) must include a `#N` issue reference and be at most 72 characters. GitHub cuts longer subjects, which hides the `#N` from tools that read them:

```bash
# Good -- references issue
git commit -m "Fix overflow on mobile (#42)"
git commit -m "Update nav styling (Part of #10)"

# Bad -- will be REJECTED by commit-msg hook
git commit -m "Fixed stuff"
git commit -m "WIP"
```

### Step 6: Push and Create a PR

```bash
git push -u origin 42-fix-overflow

# Create PR targeting main
gh pr create --title "Fix overflow on mobile" --body "Closes #42. ..."
```

- The PR description must say `Closes #N` to auto-close the issue on merge
- For sub-issues: PR says `Closes #11. Part of #10.`
- This ensures the issue is closed automatically when the PR is merged -- no manual close needed

### Step 7: Close the Issue (automatic or manual)

**Preferred -- automatic:** If the PR body contains `Closes #N`, GitHub closes the issue automatically when the PR is merged. This is the default workflow.

**Manual -- for work without a PR:** If a commit directly resolves an issue (e.g., a small fix merged without a PR), close the issue explicitly after the commit is on `main`:
```bash
gh issue close 42 --comment "Resolved in commit <sha>. Summary of what was done..."
```

**Rule:** Every issue must be closed once its associated PR is merged or its commit lands on `main`. Do not leave resolved issues open.

---

### Workflow Checklist

Before considering work "complete":
- [ ] GitHub issue exists for the work
- [ ] Issue has comments documenting findings, decisions, and design tradeoffs (alternatives considered and why they were rejected)
- [ ] Every change in the diff is explainable by something posted on the issue (plan, decision comment, or deviation note)
- [ ] Work was done on a feature branch (not `main`)
- [ ] All commit subjects reference the issue number (`#N`) within 72 characters
- [ ] PR created targeting `main` with `Closes #N` in the body
- [ ] Issue closed (automatically via PR merge, or manually if no PR)
- [ ] Epic closed (if applicable) after all sub-issues are done

### Git Hooks

`newrepo` installs and activates the hooks; `newrepo --check` audits them. By default it points `core.hooksPath` at `~/dotfiles/.githooks` rather than copying them in. Two shape every commit:

| Hook | What it does |
|------|-------------|
| `pre-commit` | Blocks commits on the repo's default branch, read from `origin/HEAD` (`main` and `master` are always blocked), and lints the staged files |
| `commit-msg` | Blocks commits whose subject lacks a `#N` issue reference or exceeds 72 characters |

Either can be bypassed with `--no-verify` in emergencies only. The other hooks, and the lint each language gets, are described under "Git Hooks" in `~/dotfiles/README.md`.

A repo may commit `.githooks-content` listing path prefixes (e.g. `blog/`) whose commits are content, not work: a commit touching **only** those paths may land on `main` with no issue reference. A repo that does this says so in its own `CLAUDE.md`; everything else it contains follows the rules above.

# Documentation Requirements

## Atomic Documentation Rule

**Documentation ships in the same commit as the code change, not in a follow-up commit or PR.** Every commit that changes behavior, adds features, modifies infrastructure, or adds dependencies must also update the relevant docs (README.md, the tool's own docs and comments) in that same commit. A code change without its documentation update is incomplete and should not be committed.

## Where each kind of text goes

- **How a tool works now** -- its README section, `SKILL.md`, script header and comments. These change in the same commit as the code.
- **Why it works that way** -- the GitHub issue: its plan, decision and deviation comments.
- **A guardrail every session must know** -- `CLAUDE.md`, one line plus an issue number. Only the human adds these.
- **A guardrail that matters only when one package's files are edited** -- `.claude/rules/<pkg>.md` with a `paths:` glob, covered by the repo's rules test where it has one, never `CLAUDE.md`. Only the human adds these too. A rule about *running* a command stays in `CLAUDE.md`: rules load after a Read, Write or Edit of a matching file, never on a Bash command (dotfiles#1030).
- **A lesson worth keeping** -- a GitHub issue labelled `lesson`, never `CLAUDE.md` or `docs/solutions` directly.
- **A lesson about one skill, once the human accepts it** -- that skill's `## Gotchas` section, so it loads only with the skill (dotfiles#1041).

## When Making Any Change

**Always update documentation as part of the same commit/PR:**

1. **README.md** - Update when you:
   - Add new features or capabilities
   - Change project structure or file organization
   - Add new dependencies or requirements
   - Modify setup procedures

2. **CLAUDE.md** - **Never add to it on your own.** It is loaded into every conversation, and a session's additions turn it into a changelog. The one exception: a change that adds a new tool may add that tool's one-line pointer in the same commit.

   When the work teaches something worth keeping -- a rule a session would otherwise get wrong, or a non-obvious lesson -- file it as an issue for the human to sweep:
   ```bash
   gh label create lesson --force --color fbca04 --description "Candidate durable lesson; the human decides where it goes"
   gh issue create --label lesson --title "<the lesson in one line>" --body-file <file>
   ```
   The body gives the context, the evidence (issue, PR, command output) and a proposed one-line rule. The human decides whether it becomes a `CLAUDE.md` guardrail, a path-scoped rule, a line in the tool's own docs, or nothing.

3. **Code Comments & Docstrings** - Update when you:
   - Add new functions or classes
   - Change function behavior or parameters
   - Add complex logic that needs explanation
   - Create workarounds or non-obvious solutions

## Documentation Checklist

Before considering a change "complete," verify:
- [ ] README.md and the tool's own docs reflect all user-visible changes
- [ ] CLAUDE.md changed only for a new tool's one-line pointer
- [ ] Any lesson worth keeping is filed as a `lesson` issue
- [ ] Code has appropriate comments for complex logic

# Python Conventions

## Virtual Environment

- **Always use a virtual environment.** Ensure a virtual environment exists (e.g. `venv/` or `.venv/`) before installing any packages. If one doesn't exist, create it before proceeding.
- Run scripts via the venv: `source venv/bin/activate` or `.venv/bin/python3 script.py`
- **`.python-version` is the interpreter version**, committed at the repo root (`newrepo --only python_version` writes one). Create a venv at that version with `uv venv --seed --python "$(head -1 .python-version | tr -d '[:space:]')" .venv` (the repo's own venv dir), which downloads the version if this machine lacks it. Without uv, `python3 -m venv` takes whatever `python3` happens to be, so check its version against the pin first. Change the pin only on purpose, in its own commit.

## Dependency Management

- **Always maintain `requirements.txt` with pinned dependencies.** Update it whenever packages are added or removed.
- After every `requirements.txt` change, run a fresh install and verify it succeeds:
  ```bash
  pip install -r requirements.txt
  ```
  If pip reports a dependency conflict, fix it before committing.
- Include the `requirements.txt` change in the same commit as the code that needs it (atomic commit rule).

## Lint, Format, Types

- **Annotate every function signature you write or change** -- each parameter and the return type. Untouched code stays as it is; no drive-by annotation.
- **A repo that commits `requirements-lint.txt` has adopted ruff and mypy** (`newrepo --only python_lint` adopts one). Its code passes its own `ruff.toml` / `mypy.ini` (or `[tool.ruff]` / `[tool.mypy]`), run at the pinned versions so the Mac and minions agree -- never a globally installed copy:
  ```bash
  uvx --from "$(grep '^ruff==' requirements-lint.txt)" ruff check --fix <files>
  uvx --from "$(grep '^ruff==' requirements-lint.txt)" ruff format <files>
  uvx --from "$(grep '^mypy==' requirements-lint.txt)" mypy --python-executable .venv/bin/python <files>
  ```
  (`venv/bin/python` where the repo uses `venv/`.) The pins stay out of `requirements.txt`, which holds the project's own dependencies.
- **After each Edit or Write of a `.py`, the `python-lint.sh` hook has already run the two ruff commands** and reports only findings new since the last commit. Fix what it reports. mypy runs at commit, when `pre-commit` warns on new ruff findings, unformatted files and mypy errors in the staged `.py` -- fix those before pushing. It never blocks unless the repo commits `.githooks-python-block`, which makes those findings block (every ruff finding, not just new ones), and a lint tool that cannot run blocks too.

## Explicit Configuration -- Never Silently Create

- **Required environment variables must be explicitly set.** If a required variable is missing, fail with a clear error message -- don't silently fall back to a default.
- **Never create top-level infrastructure directories.** Directories like `data/`, `logs/`, or any root-level resource directory must already exist. Subdirectories within them may be created as needed.
- **Never use silent fallbacks for paths.** Do not write `Path(os.getenv("SOME_DIR", "some/default"))` for required paths. If the env var is missing, raise an error.
- **Validate preconditions early.** Check that required directories, env vars, and credentials exist at startup, before doing any work.
